# pf-handoff — бюджет контекста и непрерывность сессий для Claude Code

[![tests](https://github.com/turvodnik/pf-handoff/actions/workflows/tests.yml/badge.svg)](https://github.com/turvodnik/pf-handoff/actions/workflows/tests.yml)

*Документация: [English](README.md) · русская версия (этот файл)*

Набор из правил, двух скиллов и четырёх хуков, который решает главную боль длинных сессий: **контекстное окно кончается, автокомпакт срабатывает как лотерея, агент забывает, что делал**. С pf-handoff агент заранее видит заполнение окна, сам ведёт «шпаргалку состояния» и переживает сжатие истории или смену чата так, будто ничего не случилось.

## Проблема, которую это решает

- **Контекстное окно** — рабочая память одного чата (200 тыс. или 1 млн токенов). Кончилась — Claude Code сжимает историю в короткий конспект (**компакт**), и после сжатия агент может забыть решения и состояние задачи.
- Ключевой факт: **модель не видит собственный расход окна**. Она физически не может «заранее понять, что задача не влезет» — ей никто не сообщает процент. Статус-строка (statusline) Claude Code эти данные получает, а модель — нет.
- pf-handoff строит мост: датчик → пороги → напоминания модели → шпаргалка на диске → автоподхват после сжатия.

## Как это работает (4 части)

1. **Правила** — два файла, разделённые по цене. `docs/rules-section.ru.md` — короткий раздел, который вы вставляете в CLAUDE.md/AGENTS.md: он грузится в *каждое* окно, поэтому содержит только инварианты (слои памяти, пороги окна 40/60/75%, правило реестра стаи, инструкция компактору). [`docs/context-rules.ru.md`](docs/context-rules.ru.md) — полные правила (формат HANDOFF, мультиагентность и стаи, чекпоинты, памятка «когда что нажимать»): агент читает их по требованию из копии, которая едет со скиллом (`~/.claude/skills/pf-handoff/references/context-rules.md`). Разделение снимает со старта каждой сессии ≈1,3k токенов у русского раздела и ≈600 токенов у английского (кириллица дороже в токенах).
2. **HANDOFF-файл** — живая шпаргалка состояния задачи в `<проект>/.agents/runtime/handoff/YYYY-MM-DD-<slug>.md`: Цель / Состояние (доказанное) / Следующий шаг / Блокеры / Ключевые файлы и решения / Не делать. Перезаписывается целиком, ≤120 строк, в .gitignore (когда инструменты пишут в `.agents/runtime/handoff/`, а `.gitignore` там нет, они кладут его — он игнорирует всё, кроме себя).
3. **Скиллы**:
   - `pf-handoff` — чекпоинт или закрытие сессии: сверка доказанного → перезапись шпаргалки → статусы/журнал.
   - `pf-resume` — подхват в новом чате или после `/clear`: читает шпаргалку и продолжает, «как будто чат тот же». Переоткрывает закрытый файл по slug; сам закрывает шпаргалки уже завершённых задач.
4. **Хуки** (скрипты, которые Claude Code запускает сам; каталог `hooks/`):
   - `statusline.sh` — двухстрочная богатая статус-строка (стиль ccstatusline, ноль зависимостей) и датчик, пишущий процент окна в state-файл:
     `Model: Fable 5 | Effort: medium | Context: [██░░░░░░░░░░░░░░░░░░] 110k/1.0M (11%) | ⎇ main(+0,-0)`
     `Session: 0.0% | Reset: 4hr 56m | Weekly: 18.0% | Weekly Reset: 4d 12hr 6m`
     Цвет бара следует зонам (зелёный < 40%, жёлтый 40–59%, красный ≥ 60%); Session/Weekly — лимиты подписки со временем до сброса; сегмент ветки — добавленные/удалённые строки за сессию. Сегменты мягко исчезают при отсутствии данных. Рендерится в терминале Claude Code (у других CLI нет крючка кастомной статус-строки; desktop-приложение статус-строку не рисует — там датчик работает через разбор транскрипта).
   - `context-guard.sh` — на порогах (по умолчанию **40 / 60 / 75 % окна**) вбрасывает модели короткую директиву: на 40 — короткий чекпоинт HANDOFF, крупное — субагентам; на 60 — полный `pf-handoff`, новых средних/крупных кусков не начинать; на 75 — финальный handoff, довести шаг до проверяемой точки. Вне порогов молчит. Если state-файла нет — сам считает процент из транскрипта сессии (fallback). Размер окна — тот, что последним сообщила статус-строка (число самого харнесса); без него для текущего семейства моделей предполагается 1M, а для любой другой — окно, которое guard оценил раньше, иначе 1M. **Субагентам директив не шлёт вовсе**: у них маленькое окно, и харнесс сжимает его сам, а HANDOFF принадлежит владельцу задачи, а не субагенту. Ход с серверным инструментом `advisor` считается по последней итерации основной модели, а не по удвоенной сумме, которую API сообщает для такого хода.
   - `sessionstart.sh` — после сжатия (автоматического и ручного одинаково) и при резюме говорит агенту прочитать свою шпаргалку (по `session_id`; иначе самую свежую без session id, со списком) и продолжать, и перечисляет задачи автопилота, которые в его реестре ещё помечены как запущенные; после ручного `/clear` только указывает на шпаргалку (`/pf-resume <slug>`) — продолжать или нет, решаете вы; на свежем старте только перечисляет активные шпаргалки с указателями `/pf-resume <slug>` — новый чат может быть о другой задаче; поля из файла доходят до модели не длиннее 120 знаков. Каждый старт заканчивается строкой `Сессия: <8 знаков>` — это значение для `session_id` в HANDOFF и реестре. В дочернем CLI, который запустил `council.sh` из pf-workflow (`PF_COUNCIL_RUN=1`), все хуки молчат. В каталоге, который не проект (нет ни `AGENTS.md`, ни `.agents/`), предупреждает, что снимки уйдут в глобальные папки. Заодно чистит state-файлы старше 14 суток.
   - `precompact.sh` — **ворота перед сжатием**: на каждом компакте (и ручном `/compact`, и автоматическом) зовёт `autocheckpoint.sh`, чтобы записать снимок состояния, пишет строку попытки в `~/.claude/context-state/compacts.log` и **останавливает сжатие (exit 2), если снимок не удалось записать никуда**. Подробно — ниже, [«Ворота перед сжатием»](#ворота-перед-сжатием): это единственная часть набора, которая умеет сказать «нет».
   - `autocheckpoint.sh` — в `settings.json` не регистрируется, его зовут два хука выше. Собирает снимок `<проект>/.agents/runtime/handoff/<дата>-auto-<сессия>.md` из фактов на диске (ветка, незакоммиченное, последние коммиты, открытые task-пакеты, живые шпаргалки, последние реплики человека, заполнение окна). Это *не* чекпоинт `pf-handoff`: скрипт не отличает доказанное от заявленного, он лишь гарантирует, что сжатие не произойдёт поверх пустоты.

Цена всей обвязки — **≈180 токенов на сессию в худшем случае** (все вбросы короткие и срабатывают по одному разу на порог).

### Ворота перед сжатием

Сжатие — это момент потери состояния, поэтому с v1.10.0 оно не происходит без снимка. Обычно вы этого не замечаете: снимок записан, хук молчит, сжатие идёт.

- **Когда блокирует.** Только когда снимок не удалось записать **никуда**: каталог проекта недоступен для записи *и* аварийный каталог `~/.claude/context-state/handoff` тоже; либо рядом с `precompact.sh` нет `autocheckpoint.sh`; либо в `PATH` нет ни `jq`, ни `python3` (без разбора JSON не назвать сессию — значит и снимок не записать); либо вход не разобрался вовсе. Сессия **субагента** снимок не пишет по устройству и не блокируется никогда.
- **Что вы увидите.** Сообщение `[COMPACTION STOPPED]` в stderr с причиной и выходами (по-английски, с русской строкой-выжимкой) и строку в `~/.claude/context-state/compacts.log` (`OK <файл>`, `BLOCKED-no-checkpoint`, `SKIPPED-subagent`, `SKIPPED-empty-stdin`).
- **Выходы**, по порядку: выполнить скилл `pf-handoff` руками (полный чекпоинт — после него сжатие ничего не теряет); починить права на запись в `<проект>/.agents/runtime/handoff` и `~/.claude/context-state/handoff`; поставить `jq` или `python3`; в крайнем случае удалить запись `PreCompact` из `~/.claude/settings.json` — сжатие разблокируется сразу, вместе со страховочной сеткой.
- **Почему жёсткая остановка, а не предупреждение**: сжать, не сохранив ничего, — ровно та потеря, ради которой набор и сделан, а непрочитанное предупреждение выглядит точь-в-точь как успех.

## Установка (3 шага + проверка)

Требования: macOS/Linux, **bash** (установщик регистрирует хуки, называя интерпретатор явно: на Debian/Ubuntu `/bin/sh` — это dash, который наши скрипты прочитать не может; если bash в `PATH` нет вовсе, хуки самоотключаются, а не блокируют работу), **`python3`** — он нужен установщику, и без него установщик останавливается, ничего не меняя; при работе хукам хватает `python3` или `jq` (воротам выше нужен один из них). Claude Code с поддержкой хуков и statusline.

```bash
git clone https://github.com/turvodnik/pf-handoff.git
cd pf-handoff
bash install.sh
```

Это вся автоматическая часть: установщик копирует оба скилла (обычными копиями — в `~/.claude/skills`, плюс в `~/.codex`/`~/.gemini`, если эти CLI есть на машине), регистрирует хуки в `~/.claude/settings.json` (с бэкапом; отсутствующий settings.json создаётся) и запускает проверку здоровья — все строки должны быть OK.

Единственный ручной шаг: **вставьте содержимое `docs/rules-section.ru.md`** в конец вашего `~/.claude/CLAUDE.md` (или канонического AGENTS.md при мульти-агентной схеме). Скиллы ссылаются на эти правила как на «§13» — если у вас другая нумерация, оставьте заголовок как есть или поправьте ссылки.

Заметки:
- Скиллы ставятся **копиями**, поэтому клон после установки можно перемещать или удалять; обновление — `git pull && bash install.sh`. Записи хуков в settings.json указывают на каталог `hooks/` клона — переместили клон — перезапустите `bash install.sh` с нового места. Установка из нового клона, пока зарегистрирован старый клон pf-handoff, переносит регистрации на новый (`MOVED: <событие> <старый путь> → <новый путь>`); до этого `doctor.sh` печатает `WARN` по каждой.
- Если скилл уже существует как **симлинк** (вы управляете скиллами своим механизмом) — установщик его пропустит и скажет об этом.
- Всё идемпотентно: повторный запуск не плодит дублей. С v1.10.0 установщик ещё и **переписывает свои устаревшие записи хуков**, а не оставляет их как есть: обновляясь с v1.9.0 и раньше, запустите `bash install.sh` один раз — иначе в вашем `settings.json` осталась бы старая регистрация (та, что ломала все хуки на Debian/Ubuntu).
- **Чужие регистрации остаются (с 2.0.0).** Если хук или `statusLine` уже зарегистрирован, а его команда называет существующий файл вне этого клона (другая копия этих хуков, чекпоинт мастерской автора, ваш собственный скрипт статус-строки), установщик его не трогает и печатает по каждой такой записи:
  `KEPT: <событие> → <путь> (registered elsewhere; re-run with --force to point it at this clone)`
  Команда `statusLine`, в которой вообще нет пути к файлу (`npx ccusage statusline`, `ccstatusline`), тоже остаётся. Путём к файлу считается слово, которое начинается с `/`, `~`, `./`, `../` или `$` (`$HOME`/`${HOME}` раскрываются): `npx @scope/pkg` или `sed s/a/b/` — это команда, а не путь. Регистрация на файл, которого уже нет, чинится как раньше. `bash install.sh --force` переводит всё на этот клон. `doctor.sh` считает KEPT исправным и называет путь или команду. Пользователям Orca: собственная статус-строка Orca остаётся (KEPT); без нашей статус-строки хуки не узнают настоящее окно модели. Guard тогда считает заполнение по транскрипту сессии, а окно вынужден угадывать по имени модели: 1M предполагается и для текущего семейства моделей, и для любой другой. На модели с окном 1M подсказки 40/60/75 % приходят как обычно. На модели с окном 200k они не приходят вовсе — 170k токенов читаются как 17 %, — и первым вы увидите сжатие платформы. Если вы работаете на модели с окном 200k, запустите `bash install.sh --force` (наша статус-строка сообщает настоящее окно).
- **Если вы ставили версию до 2.0.0**: прежний установщик заменял вашу `statusLine` своей. Прежнее значение лежит в **самом раннем** бэкапе настроек `<файл настроек>.bak-<YYYYMMDD-HHMMSS>` рядом с `~/.claude/settings.json` — сделанном до первой установки pf-handoff; в более поздних уже наша строка. Самый ранний — первая строка `ls -1 ~/.claude/settings.json.bak-* | sort | head -1`. Чтобы вернуть, скопируйте блок `statusLine` из бэкапа в файл настроек и запустите `bash install.sh` снова — чужая строка состояния теперь остаётся (KEPT).
- `.claude-plugin/plugin.json` нужен только для `claude plugin validate`/`eval` — поле `hooks` в нём не объявлено, поэтому установка репозитория как плагина не навешивает четыре хука выше второй раз; путь установки — по-прежнему `install.sh` (запись в `~/.claude/settings.json`).

### Обновление

```bash
cd <ваш клон> && git pull && bash install.sh
```

Записи хуков в `settings.json` указывают в клон, поэтому `git pull` уже обновляет хуки; скиллы — копии, поэтому установщик запускается снова и обновляет их. pf-handoff самодостаточен — ставится и обновляется отдельно, общего установщика нет.

Обновляетесь с v1.10.0: теперь хуки кладут `.gitignore` и в уже существующий `.agents/runtime/handoff/`, но снимки, закоммиченные раньше, остаются в git — проверьте `git ls-files .agents/runtime/handoff` и, если список не пуст, уберите их из индекса: `git rm -r --cached .agents/runtime/handoff`.

Удаление — снять только наши записи, сохранив остальные настройки (восстановление старого бэкапа откатило бы всё, что записано после него). Запускать из клона; файл настроек сначала копируется:

```bash
cp ~/.claude/settings.json ~/.claude/settings.json.bak-before-uninstall
python3 - ~/.claude/settings.json "$PWD/hooks/" <<'EOF'
import json, sys
path, ours = sys.argv[1], sys.argv[2]
d = json.load(open(path, encoding="utf-8"))
mine = lambda c: ours in str(c or "").replace("'\\''", "'")
hooks = d.get("hooks") or {}
for evt in list(hooks):
    for g in hooks[evt]:
        g["hooks"] = [h for h in g.get("hooks", []) if not mine(h.get("command"))]
    hooks[evt] = [g for g in hooks[evt] if g.get("hooks")]
    if not hooks[evt]:
        del hooks[evt]
if mine((d.get("statusLine") or {}).get("command")):
    del d["statusLine"]
json.dump(d, open(path, "w", encoding="utf-8"), indent=2, ensure_ascii=False)
EOF
```

Затем удалите копии скиллов: `rm -rf ~/.claude/skills/pf-handoff ~/.claude/skills/pf-resume` (и те же две папки в `~/.codex/skills` и `~/.gemini/skills`, если они есть) и раздел правил, который вы вставили в `~/.claude/CLAUDE.md`.

## Настройка

Пороги окна — по умолчанию **40 / 60 / 75 %** окна модели (40 — короткий чекпоинт HANDOFF, крупное — субагентам; 60 — полный `pf-handoff`, новых средних/крупных кусков не начинать; 75 — финальный handoff, довести шаг до проверяемой точки). Чтобы изменить, задайте переменную окружения `CONTEXT_GUARD_THRESHOLDS` — три целых через пробел по возрастанию, каждое 1–99:

```bash
export CONTEXT_GUARD_THRESHOLDS="30 50 70"
```

Любое другое значение молча игнорируется, действуют дефолты. Цвет статус-бара следует тем же значениям (жёлтый с первого, красный со второго). Файла порогов на проект больше нет.

Само сжатие делает платформа, а не хуки: **80 % окна 1M, 90 % окна 200k** (80 % на маленьком окне — слишком рано). Задаётся на модель командой `/autocompact` — значение считается в токенах, не в процентах: `/autocompact 800000` для окна 1M, `/autocompact 180000` для окна 200k. Перед каждым сжатием хуки пишут снимок состояния (см. «Ворота перед сжатием» выше).

Вид и виджеты статус-строки — `~/.config/pf-handoff/statusline.json` (опционален; без него — дефолтный вид):

```json
{
  "line1": ["model", "effort", "context", "branch"],
  "line2": ["session", "weekly"],
  "bar_width": 20,
  "bar_filled": "█",
  "bar_empty": "░",
  "separator": " | ",
  "colors": true
}
```

- Виджеты: `model`, `effort` (уровень размышления модели, если CLI его сообщает), `context` (бар + токены/окно + %), `branch` (git-ветка со счётчиком +/− строк сессии), `session` (лимит 5-часового окна % + Reset), `weekly` (недельный % + Weekly Reset), `cost` (стоимость сессии в USD), `duration` (длительность сессии). Неизвестные имена молча пропускаются; виджет без данных исчезает сам.
- **Отсутствующий** ключ `line1`/`line2` оставляет дефолт; **явно пустой** массив (`"line2": []`) отключает строку.
- `bar_width` — от 5 до 60; `colors: false` — чистый текст без ANSI.

Быстрый старт и мгновенная обратная связь:

```bash
mkdir -p ~/.config/pf-handoff && cp examples/statusline.json ~/.config/pf-handoff/
bash hooks/statusline.sh --preview   # мгновенный рендер с примерными данными — правьте конфиг и запускайте снова
bash hooks/doctor.sh                 # заодно проверяет конфиг и говорит, ПОЧЕМУ он был бы проигнорирован
```

## Что важно знать

- **Ваш прежний statusline**: если он уже есть, `install.sh` его оставляет (KEPT, см. «Установка»); заменяется нашей только пустая или битая регистрация. Чтобы использовать нашу, запустите `bash install.sh --force`; прежняя строка останется в бэкапе настроек `<файл настроек>.bak-<YYYYMMDD-HHMMSS>`. Чтобы совместить обе, загляните в `hooks/statusline.sh` и позовите свой скрипт из него по образцу вызова Orca.
- **Orca опциональна**: обёртка вызывает скрипт Orca только если он существует; на машине без Orca всё работает без изменений.
- **Режимы разрешений**: хуки работают во всех режимах, включая bypass permissions — режим влияет только на вопросы «разрешить инструмент?».
- **Headless (`claude -p`)** не запускает SessionStart-хук и statusline — там агента ведут правила (он сам ищет шпаргалку), а процент guard считает из транскрипта.
- **Субагенты**: у каждого своё свежее окно — это главная защита оркестраторов. Guard не шлёт субагенту директив порогов (субагента он узнаёт по `agent_id` во входе хука или по его собственному транскрипту в каталоге `subagents/` сессии). Правило из `docs/context-rules.ru.md`: субагент пишет **полный** результат в файл (ничего не теряется — важно для фокус-групп и исследований), а в чат родителя возвращает только короткую сводку. Для больших стай (десятки агентов) — перед запуском волны чекпоинт реестра «агент → задача → файл результата» в HANDOFF: даже если окно оркестратора сожмётся посреди полёта, он точно знает, чего ждёт. Проверено на **любой глубине вложенности** (дети, внуки, …): каждый уровень получает собственный agent id и плоский транскрипт в каталоге `subagents/` сессии, поэтому guard узнаёт каждого.
- **Известное ограничение — чужой хук с тем же именем файла**: регистрация, которая указывает на `precompact.sh`, `sessionstart.sh` или `context-guard.sh` другого инструмента (рядом нет наших скриптов), остаётся, и наш хук для этого события не ставится; установщик печатает `WARN: KEPT: …`, `doctor.sh` — `WARN`. `bash install.sh --force` заменяет её и перед этим называет старую команду строкой `REPLACED: <событие> <старая команда> → <наш скрипт>`.
- **Честное ограничение**: конспект компакта и шпаргалка сохраняют рабочее состояние (цель, решения, следующий шаг, отменённое), но не дословную память всего чата. Дословное — в транскрипте сессии и журнале проекта.

## Для вашего ИИ-агента

Шаги, которые ИИ-агент (Claude Code, Codex, …) выполнит дословно. Скажите ему: *«Установи pf-handoff по разделу „Для вашего ИИ-агента“ его README»*.

1. **Проверь требования.** `command -v bash git python3` должна напечатать три пути (`jq` — по желанию). Нет `python3` — остановись и скажи человеку: установщику он нужен.
2. **Установи.** Клон потом не удаляй: хуки запускаются из его каталога `hooks/`.
   ```bash
   git clone https://github.com/turvodnik/pf-handoff.git ~/pf-handoff
   cd ~/pf-handoff && bash install.sh
   ```
3. **Прочитай вывод установщика.**
   - `KEPT: <событие> → <путь>` — эта регистрация чужая (другой инструмент, собственная строка состояния человека) и оставлена как есть. Назови её человеку; `bash install.sh --force` (переводит всё на этот клон) — только после его «да».
   - `WARN: KEPT: <событие> → <путь> is not a pf-handoff hook …` — файл другого инструмента с нашим именем; наш хук для этого события НЕ установлен. Назови это человеку; `--force` заменяет его (строка `REPLACED:` называет заменённое) — только после его «да».
   - `MOVED: <событие> <старый путь> → <новый путь>` — старый клон pf-handoff заменён этим. Делать ничего не нужно.
   - `SKIP: …` — папка скилла — симлинк или чужая папка. Назови её человеку.
4. **Проверь.** `bash hooks/doctor.sh` — все строки `OK`, код выхода 0. Строка `WARN` говорит, что не так и как поправить; строка `FAIL` называет поломку.
5. **Правила (сначала спроси человека — это его файл).** Допиши часть `docs/rules-section.ru.md` (или `docs/rules-section.md`) ниже строки `---` в конец `~/.claude/CLAUDE.md`.
6. **Перезапусти Claude Code** (новая сессия), чтобы подхватились хуки и строка состояния.

Что ставится: скиллы `pf-handoff` и `pf-resume` (копии в `~/.claude/skills`, плюс `~/.codex/skills` и `~/.gemini/skills`, если эти папки есть); четыре регистрации хуков в `~/.claude/settings.json` — `UserPromptSubmit` и `PostToolUse` → `hooks/context-guard.sh`, `SessionStart` → `hooks/sessionstart.sh`, `PreCompact` → `hooks/precompact.sh`; строка состояния → `hooks/statusline.sh`. Файл настроек сначала копируется в бэкап (`settings.json.bak-<YYYYMMDD-HHMMSS>`).

Обновление: `cd ~/pf-handoff && git pull && bash install.sh`, затем снова шаг 4.

Как начать — что человек говорит агенту: «сделай хендофф» или `/pf-handoff` (сохранить состояние задачи сейчас); `/pf-resume` в новом чате (подхватить работу). Больше ничего не нужно: подсказки на 40/60/75 % и снимок перед сжатием приходят сами.

## Памятка «когда что нажимать»

| Ситуация | Действие |
|---|---|
| Большая задача на автомате | ничего — агент чекпоинтит сам, автокомпакт + хук подхватят |
| Почистить окно, остаться в чате | `/compact` (агент перед этим сам сделает чекпоинт) |
| Пауза | `/pf-handoff`, потом просто продолжайте |
| Закрыли терминал | `claude --continue` |
| Новый чат | `/pf-resume` |
| Начисто в том же окне | `/pf-handoff` → `/clear` → `/pf-resume` |
| Несвязанная новая задача | `/clear` без resume |

## Разработка

Канон разработки сейчас живёт в приватном `_tools` владельца (skill-library + context-hooks); этот репозиторий — дистрибутив. Перед релизом: `bash sync-from-tools.sh` → `git diff` → запись в `CHANGELOG.md` (обе языковые версии) и `"version"` в `.claude-plugin/plugin.json` → коммит → тег `vX.Y.Z`. Версионирование — semver: ломающие изменения (формат HANDOFF, имена state-файлов, контракт скиллов) = major.

Прогнать тесты локально: `bash tests/run.sh` (bash 3.2+, coreutils, `jq` и `python3` — матрица «хуки никогда не падают» строит курированные PATH-песочницы jq-only/python3-only и обрывается без любого из них, это не честный пропуск. ShellCheck, PyYAML и actionlint — единственные по-настоящему опциональные части, пропускаются с указанием причины при отсутствии). Та же команда — в CI на каждый push и pull request ([`.github/workflows/tests.yml`](.github/workflows/tests.yml)).

**pf-handoff полностью самостоятелен** — ему не нужен ни трекер задач, ни тикеты, ни какие-либо другие инструменты. Правила упоминают журнал решений и task-пакеты; если вы ими не пользуетесь — соответствующие шаги просто не применяются (см. примечание в начале `docs/rules-section.ru.md`).

**Опциональный компаньон — [pf-workflow](https://github.com/turvodnik/pf-workflow)**, конвейер задач автора. pf-handoff полностью работает сам; ставьте pf-workflow, если поверх защиты контекста нужен ещё и дисциплинированный процесс поставки. Что он даёт:
- `pf-spec` — допрос, который превращает смутную идею в спецификацию *до* начала работы;
- `pf-tickets` — разбивка спеки на самодостаточные task-пакеты, которые свежая сессия исполняет без истории вашего чата;
- `pf-do` + ревью — контракт исполнителя с доказательной приёмкой: каждый критерий подтверждается свежим выводом команды, «должно работать» не считается;
- `pf-replan` — смена курса без потери сделанного; `pf-retro` — регулярные ретро процесса.

Если установлены оба — сцепляются автоматически, без настройки: HANDOFF-файлы ссылаются на тикеты в поле `task:`, исполнитель проверяет активный HANDOFF перед стартом, смена курса обновляет «Не делать», ретро просматривает лог компактов.

Одна сцепка выходит за пределы бесплатных инструментов машины, поэтому строго опциональна. Должны совпасть четыре условия: установлен pf-workflow (он поставляет скрипт ревью), на машине есть OpenAI Codex CLI, в проекте лежит `.agents/codex-review.json` со значением `{"enabled": true}`, и в закрываемой сессии остался незакоммиченный код. Тогда при закрытии запускается ревью этого кода в режиме read-only, а путь к отчёту попадает в HANDOFF. Codex — платный сторонний CLI; нет любого из четырёх условий — шаг молча пропускается, ровно как раньше.

## Мини-глоссарий

- **Токен** — единица объёма текста для модели (≈3,5 символа смешанного текста).
- **Компакт/автокомпакт** — сжатие истории чата в конспект: руками `/compact` или автоматически у края окна.
- **Хук (hook)** — ваш скрипт, который Claude Code запускает сам на событии (старт сессии, перед сжатием и т.п.).
- **additionalContext** — механизм, которым хук вбрасывает модели короткую служебную заметку.
- **State-файл** — файлик-датчик (`~/.claude/context-state/<session>.json`), через который статус-строка сообщает хукам текущий процент окна.
- **Fallback (запасной путь)** — если датчик молчит, процент пересчитывается из транскрипта сессии.
